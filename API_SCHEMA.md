# AuraBrief 95 — API & Event Schema Specification

> **Purpose:** This document defines the exact JSON schemas, event stream payloads, and API contracts.  
> **Audience:** All team members — especially M5 (integration) and M1 (AI/ML ranking).  
> **Rule:** If you change a schema, update this doc first and notify the team.

---

## 1. Common Event Schema

Every event from all 3 streams follows this base structure:

```json
{
  "event_id": "string (UUID v4)",
  "source": "string (enum: infra-monitor | app-errors | deploy-events)",
  "timestamp": "string (ISO-8601, e.g. 2026-08-23T08:30:00Z)",
  "severity": "string (enum: critical | warning | info)",
  "service": "string (enum: payment-api | user-service | gateway | order-service | auth-service)",
  "region": "string (enum: us-east | eu-west | ap-south)",
  "title": "string (human-readable summary, max 120 chars)",
  "details": "object (stream-specific payload — see below)",
  "tags": "array of strings"
}
```

### Field Definitions

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `event_id` | `string` | ✅ | UUID v4. Generated by the simulator. Globally unique. |
| `source` | `string` | ✅ | Which stream sent this. One of: `infra-monitor`, `app-errors`, `deploy-events` |
| `timestamp` | `string` | ✅ | ISO-8601 UTC. When the event occurred. |
| `severity` | `string` | ✅ | `critical` (immediate action), `warning` (attention needed), `info` (awareness) |
| `service` | `string` | ✅ | Which microservice is affected. |
| `region` | `string` | ✅ | Deployment region where the event originated. |
| `title` | `string` | ✅ | One-line human-readable summary. |
| `details` | `object` | ✅ | Stream-specific data (schema varies per `source` — see Section 2). |
| `tags` | `string[]` | ✅ | Categorization labels. At least 1 tag required. |

### Severity Mapping (for M1 — Ranking)

| Severity | Numeric Score (0-1) | Meaning |
|----------|---------------------|---------|
| `critical` | 1.0 | Service down, data loss risk, customer-facing impact |
| `warning` | 0.6 | Degraded performance, threshold breach, needs attention |
| `info` | 0.2 | Routine event, deployment started, config change |

### Service Criticality Tiers (for M1 — Business Impact score)

| Service | Tier | Impact Score (0-1) | Rationale |
|---------|------|-------------------|-----------|
| `payment-api` | Tier 1 | 1.0 | Revenue-critical |
| `gateway` | Tier 1 | 0.9 | All traffic flows through it |
| `auth-service` | Tier 2 | 0.7 | Login failures block users |
| `order-service` | Tier 2 | 0.6 | Core business function |
| `user-service` | Tier 3 | 0.4 | Profile/settings, non-blocking |

## 2. Stream-Specific `details` Payloads

### Stream 1: `infra-monitor` (Infrastructure Monitoring)

Simulates CPU, memory, disk, and container health events.

```json
{
  "metric": "string (enum: cpu_usage | memory_usage | disk_usage | container_restarts)",
  "current_value": "number (the observed metric value)",
  "threshold": "number (the threshold that was breached)",
  "unit": "string (enum: percent | count | GB)",
  "host": "string (e.g. node-us-east-01)",
  "duration_seconds": "number (how long the condition has persisted)"
}
```

**Example:**
```json
{
  "event_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "source": "infra-monitor",
  "timestamp": "2026-08-23T08:30:00Z",
  "severity": "critical",
  "service": "payment-api",
  "region": "us-east",
  "title": "CPU usage at 95% on payment-api node",
  "details": {
    "metric": "cpu_usage",
    "current_value": 95.2,
    "threshold": 80.0,
    "unit": "percent",
    "host": "node-us-east-01",
    "duration_seconds": 300
  },
  "tags": ["infrastructure", "performance", "cpu"]
}
```

---

### Stream 2: `app-errors` (Application Errors)

Simulates HTTP error spikes, latency breaches, exception bursts, and circuit breaker events.

```json
{
  "error_type": "string (enum: http_5xx_spike | latency_p99_breach | exception_burst | circuit_breaker_open)",
  "error_count": "number (count of errors in the window)",
  "time_window_seconds": "number (observation window, e.g. 60, 300)",
  "endpoint": "string (e.g. /api/v1/payments/process)",
  "error_rate_percent": "number (error rate as percentage of total requests)",
  "sample_error": "string (one representative error message)"
}
```

**Example:**
```json
{
  "event_id": "b2c3d4e5-f6a7-8901-bcde-f12345678901",
  "source": "app-errors",
  "timestamp": "2026-08-23T08:31:15Z",
  "severity": "critical",
  "service": "payment-api",
  "region": "us-east",
  "title": "HTTP 5xx spike: 23% error rate on /payments/process",
  "details": {
    "error_type": "http_5xx_spike",
    "error_count": 347,
    "time_window_seconds": 300,
    "endpoint": "/api/v1/payments/process",
    "error_rate_percent": 23.4,
    "sample_error": "java.sql.SQLTransientConnectionException: Connection pool exhausted"
  },
  "tags": ["application", "errors", "http-5xx"]
}
```

---

### Stream 3: `deploy-events` (Deployment Pipeline)

Simulates deploy starts, failures, rollbacks, and config changes.

```json
{
  "deploy_type": "string (enum: deploy_started | deploy_failed | rollback_triggered | config_change)",
  "version_from": "string (semver, e.g. v2.3.1)",
  "version_to": "string (semver, e.g. v2.4.0)",
  "deployed_by": "string (username or CI bot name)",
  "commit_sha": "string (short git SHA, e.g. a1b2c3d)",
  "failure_reason": "string | null (only for deploy_failed / rollback_triggered)"
}
```

**Example:**
```json
{
  "event_id": "c3d4e5f6-a7b8-9012-cdef-123456789012",
  "source": "deploy-events",
  "timestamp": "2026-08-23T08:29:00Z",
  "severity": "warning",
  "service": "gateway",
  "region": "eu-west",
  "title": "Deploy failed: gateway v2.4.0 in eu-west",
  "details": {
    "deploy_type": "deploy_failed",
    "version_from": "v2.3.1",
    "version_to": "v2.4.0",
    "deployed_by": "ci-bot",
    "commit_sha": "a1b2c3d",
    "failure_reason": "Health check timeout after 120s"
  },
  "tags": ["deployment", "failure", "ci-cd"]
}
```

## 3. API Endpoints — Request/Response Contracts

### 3.1 `POST /api/events/ingest`

**Purpose:** Receive a batch of events from any stream.

**Request Body:**
```json
{
  "events": [
    { /* Common Event Schema (see Section 1) */ },
    { /* ... */ }
  ]
}
```

**Response (200 OK):**
```json
{
  "status": "accepted",
  "received_count": 5,
  "event_ids": ["a1b2...", "b2c3...", "c3d4...", "d4e5...", "e5f6..."]
}
```

**Response (422 Validation Error):**
```json
{
  "detail": [
    {
      "loc": ["body", "events", 0, "severity"],
      "msg": "value is not a valid enumeration member",
      "type": "value_error"
    }
  ]
}
```

### 3.2 `GET /api/triage/current`

**Purpose:** Get the current ranked/prioritized events with explanations.

**Query Params (all optional):**
| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `limit` | `int` | `20` | Max events to return |
| `min_score` | `float` | `0.0` | Filter events below this score |
| `source` | `string` | `null` | Filter by stream source |

**Response (200 OK):**
```json
{
  "triage_id": "uuid (snapshot ID for replay)",
  "generated_at": "2026-08-23T08:35:00Z",
  "total_events": 42,
  "ranked_events": [
    {
      "event_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
      "source": "infra-monitor",
      "timestamp": "2026-08-23T08:30:00Z",
      "severity": "critical",
      "service": "payment-api",
      "region": "us-east",
      "title": "CPU usage at 95% on payment-api node",
      "details": { /* stream-specific */ },
      "tags": ["infrastructure", "performance", "cpu"],
      "score": 0.92,
      "score_breakdown": {
        "severity": 0.30,
        "frequency": 0.16,
        "recency": 0.14,
        "anomaly": 0.18,
        "business_impact": 0.14
      },
      "rank": 1,
      "explanation": "Critical CPU spike on payment-api (Tier 1 service) in us-east. CPU at 95% has persisted for 5 minutes, exceeding the 80% threshold. This is anomalous — baseline CPU for this service is typically 45%. Immediate attention recommended as payment processing may be degraded."
    }
  ],
  "weights_used": {
    "severity": 0.30,
    "frequency": 0.20,
    "recency": 0.15,
    "anomaly": 0.20,
    "business_impact": 0.15
  }
}
```

### 3.3 `GET /api/triage/history`

**Purpose:** Replay past triage decisions.

**Query Params:**
| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `limit` | `int` | `10` | Number of past triage snapshots |

**Response (200 OK):**
```json
{
  "history": [
    {
      "triage_id": "uuid",
      "generated_at": "2026-08-23T08:35:00Z",
      "total_events": 42,
      "top_event_title": "CPU usage at 95% on payment-api node",
      "top_score": 0.92
    }
  ]
}
```

**To get full details of a past triage:** `GET /api/triage/history/{triage_id}`

### 3.4 `POST /api/feedback`

**Purpose:** Adjust ranking weights (operator feedback loop — bonus feature).

**Request Body:**
```json
{
  "weights": {
    "severity": 0.35,
    "frequency": 0.15,
    "recency": 0.15,
    "anomaly": 0.20,
    "business_impact": 0.15
  }
}
```

> **Validation:** All weights must be between 0.0 and 1.0, and must sum to 1.0.

**Response (200 OK):**
```json
{
  "status": "weights_updated",
  "previous_weights": { "severity": 0.30, "...": "..." },
  "new_weights": { "severity": 0.35, "...": "..." },
  "message": "Rankings will reflect new weights on next triage refresh."
}
```

## 4. Simulator Behavior

The simulator runs as a separate Docker service and sends batches of events to `POST /api/events/ingest` on a configurable interval.

| Config | Env Var | Default | Description |
|--------|---------|---------|-------------|
| API URL | `API_URL` | `http://backend:8000` | Backend base URL |
| Interval | `STREAM_INTERVAL` | `5` | Seconds between batches |

### Simulation Pattern

Each cycle (every `STREAM_INTERVAL` seconds), the simulator:
1. Generates 1-3 events per stream (3-9 total per cycle)
2. Randomly assigns severity, service, region
3. Occasionally generates **correlated events** (e.g., deploy failure → error spike → CPU spike on the same service)
4. POSTs the batch to `/api/events/ingest`

### Correlation Scenarios (for realistic demo)

| Scenario | Events generated together |
|----------|--------------------------|
| **Bad deploy** | `deploy_failed` on service X → `http_5xx_spike` on service X → `cpu_usage` spike on service X |
| **Infrastructure cascade** | `memory_usage` critical on node → `container_restarts` on same node → `latency_p99_breach` on hosted service |
| **Routine noise** | `config_change` (info) + `deploy_started` (info) — low-severity background events |
